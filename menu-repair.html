Menu elements: repairing invalid content

David Grogan, Google
Lucas Radaelli, Google

Follow-up to w3c/aria#2782.

We are adding menu elements to HTML

ElementImplicit role
<menubar>menubar
<menulist> (a popover)menu
<menuitem>menuitem
<menuitemcheckbox>, <menuitemradio> menuitemcheckbox, menuitemradio
<submenu>none (display: contents)

Keyboard model follows the APG menu / menubar pattern. Explainer · whatwg/html#12011

Arrow keys move between menuitems, one tab stop for the whole menu, Esc closes the current menulist and returns focus to its invoker.

Application menus, not navigation menus

These

  • File / Edit / View menubars
  • “Actions ▾” buttons
  • Table column menus
  • Video player settings

Not these

  • Site navigation
  • Links in a <nav>
  • Disclosure navigation

<a> isn’t allowed in a menu.

Navigation menus will get a separate proposal (OpenUI #1193).

Video player settings: Chrome’s own built-in video controls use menu roles. The ⋮ overflow menu is role=menu, and its items are <label role=menuitem> elements wrapping a <button>. The Playback speed and Captions submenus are role=menu with menuitemcheckbox items, and a “Back to options” header that is role=button, i.e. a button directly inside a menu (see blink/renderer/modules/media_controls/elements/).

Example markup

<menubar>
  <submenu>
    <menuitem>File</menuitem>
    <menulist>
      <menuitem>New</menuitem>
      <menuitem>Share…</menuitem>
      <submenu>
        <menuitem>Open Recent</menuitem>
        <menulist>…</menulist>
      </submenu>
      <hr>
      <menuitem>Save</menuitem>
      …
    </menulist>
  </submenu>
</menubar>
<!-- Or from any button: -->
<button commandfor=file
        command=toggle-popover>
  File
</button>

<menulist id=file>
  <menuitem>New</menuitem>
  …
</menulist>

No ARIA, no JS. The accessibility tree is the interesting part.

Go quickly. The button gets implicit aria-haspopup=menu and aria-expanded.

Changed since we presented to ARIA in May: submenus used to be connected with ID references (command=toggle-menu commandfor=…). Now they’re nested in the DOM with <submenu>, and the toggle-menu command is gone; a button opens a standalone menulist with toggle-popover or popovertarget.

The content model

Allowed

  • Menu items: <menuitem> and its checkbox and radio versions
  • <submenu> = menuitem + menulist
  • Separators and groups: <hr>, <fieldset>, <div>

Not allowed

  • Other interactive elements: <button>, <input>, …
  • <a> (hidden by default)
  • Text outside a <menuitem> or <legend>

Text and images go inside a menuitem. The arrow keys only stop on menuitems.

This content model is stricter than ARIA’s. The big difference: HTML forbids interactive content inside a menuitem (no button, link, input or tabindex inside it), while ARIA allows it. The menuitem role puts no limits on its children, and its children aren’t presentational.

Anchors get a default display: none in menus.

Same menu, but Share… is a <button> instead of a <menuitem>. Arrow keys only stop on menuitems, so the button gets skipped. A sighted mouse user can still click it. A sighted keyboard user can see it and get frustrated, but a screen-reader user never learns it exists.

Improving the broken experience

Like <select>, which falls back when it has interactive content.

The goal: less confusing, not fixed

  • Only the author can really fix it: put the content in menuitems, or don’t use a menu
  • The browser can only make a broken menu less confusing
  • Using roles that already exist, so the keyboard and the announcements agree
  • And tell the author: a DevTools console warning, and a red squiggle on the element in DevTools

Success means screen-reader users can find and use everything. It won’t be a great menu.

Set expectations before the options: none of these attempts produce a good experience. Each one tries to describe broken content honestly using semantics that already exist, rather than inventing new ones.

Modeled on customizable <select>

When a <select> picker has interactive content, it becomes a dialog and Tab reaches everything. Menus nest, so we can’t just copy that. Two directions:

  1. Change the keyboard and roles so everything is reachable
    • Consistent, but which roles?
  2. Let arrow keys reach non-menuitems; keep the menu roles
    • Smallest change, but a menu then owns things it isn’t allowed to own

We’ve been working on (a). These two are where we want feedback.

Why not a straight copy of <select>: a select has one popup, so one dialog. Menus nest, so “dialog everywhere” gives nested dialogs (attempt 1).

If someone suggests hiding the menu or the invalid content (display: none): we decided against that for customizable select in openui#540 (2022), and we’re following that precedent.

  • It’s hard to unbreak things. If we hide the content, pages come to rely on that, and we can’t allow it later even once it can be made accessible. For select, that was secondary actions (buttons in options). For menus, we don’t want to paint ourselves into a corner and limit what ARIA actions could do.
  • Authors would fall back to <div>s, which are less accessible and get no warnings or guidance.
  • HTML doesn’t remove or hide author content. Content silently disappearing would confuse authors.
  • Instead: repair it, warn the developer, and keep the door open to improving it later.

Attempt 1: dialog + Tab

menubar          → dialog
  menuitem File
  menulist       → dialog
    menuitem New
    button Share
    …
  • One violation anywhere switches the whole menu tree, so users never mix Tab and arrows in one menu
  • Discussed in #2782
  • Tab replaces arrow keys
  • ✗ Every submenu became a nested dialog

Menuitems kept their menuitem role in attempts 1 and 2.

Scott O’Hara hinted at this back in May (at OpenUI, not in the ARIA discussion): when a menu tree has invalid content, probably leave the top-level menubar as something other than a dialog.

Lucas said he has never run into nested dialogs in the wild.

Attempt 2: dialog outside, lists inside

menubar          → dialog
  menuitem File
  menulist       → list
    menuitem New
    button Share
    …
  • No more nested dialogs
  • X of Y now counts the invalid content too
  • ✗ Esc doesn’t “close” the dialog

Focus stays on the menubar. SR users expect a dialog to close and focus to move, but a menubar can’t close.

With the button counted, the broken File menu is “X of 6” again (New 1, Share… 2, Open Recent 3, …) instead of “X of 5” with the button left out.

Attempt 3: lists everywhere

menubar              → list
  menuitem File      → listitem
  menulist           → list
    menuitem         → listitem
    menuitemcheckbox → checkbox
    menuitemradio    → radio
    button Share
  • Items leave the menu roles, or NVDA keeps saying “menu”
  • Checkable items: checkbox/radio
  • ✗ listitem can’t be expanded or collapsed
  • ✗ NVDA sometimes said “submenu”: only the HTML tag name

This is what Chromium does today (Oct 2026). NVDA seemed confused. TODO: add the exact NVDA output.

Why checkbox/radio: ARIA’s listitem supports only aria-posinset and aria-setsize, so it can’t be checked. For the same reason it can’t be expanded or collapsed, so “Open Recent” loses its submenu state. NVDA still sometimes said “submenu”, even though that word now only exists as the HTML tag name.

Attempt 4 (not tried yet): tree

menubar          → tree
  menuitem File  → treeitem
  menulist       → group
    menuitem     → treeitem
    button Share
  • treeitem supports aria-expanded and aria-checked
  • But a tree is navigated with arrow keys, not Tab…
  • …and it’s a big stretch for a menubar

How do screen readers handle a button inside role=menu?

That's option (b) from earlier. This is the main question for the group.

What about standardization?

ARIA, Handling author errors:

User agents are not responsible for logical validation, such as the following: […]

4. Elements that do not correctly observe required child / parent role relationships or that appear elsewhere than in their required parent.

So any repair is currently up to each browser.

With native elements, the browser knows the roles are wrong, because it assigned them.

Alternative: a documented heuristic?

Browser accessibility heuristics already lists:

  • aria-hidden on the root is ignored (now in the spec)
  • Data tables vs. layout tables
  • Erroneous aria-modal ignored (WebKit)

Where should menu repair go? HTML? HTML-AAM? ARIA? That list?

Interop matters: if Chromium repairs to lists and another engine repairs differently, screen-reader users get different experiences on the same page.
